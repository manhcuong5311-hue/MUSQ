- Cache reuse depends on routing. Cached states live on individual machines, traffic above about 15 requests per minute can be overflow-routed, and a request reuses a prefix only if it reaches a machine holding the entry. One write per 30-minute window is a best case; check cache_write_tokens in production.
  src: https://developers.openai.com/api/docs/guides/prompt-caching#cache-location (Undated guide, accessed 2026-11-22)

- On supported GPT-6+ models, a configuration_update input item can change reasoning effort (and text.format) while the request-level reasoning.effort and the cached prefix stay unchanged. Example: raise effort only for complex mixed dishes without losing the cached table. Changing request-level reasoning.effort instead can rewrite hidden instructions and break the cache. The docs describe this for conversations, so test it in single-turn scans.
  src: https://developers.openai.com/api/docs/guides/reasoning#change-reasoning-mid-conversation (Undated guide, accessed 2026-11-22)

- Alternative to explicit mode: implicit-mode lookups also check the end of the initial developer-message block. A prewarm request with only the fixed table (billed at the write rate) therefore lets later default-mode scans read the table from cache. Each scan would still write through the photo at 1.25x, so explicit mode stays cheaper.
  src: https://developers.openai.com/api/docs/guides/prompt-caching#how-prefix-matching-works (Undated guide, accessed 2026-11-22)
